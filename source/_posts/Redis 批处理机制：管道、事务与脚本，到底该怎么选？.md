平时我们在使用 Redis 时，通常是“发一条命令，等一个回复”。如果遇到要执行大量命令的场景，网络往返时间（RTT）就会成为最大的性能瓶颈。

为了解决这个问题，Redis 提供了三种“批量处理”机制：**管道（Pipeline）、事务（Transaction）和脚本（Lua Script）**。

很多人一看到“事务”两个字，就习惯性拿 MySQL 来套，觉得它们都是“打包执行，要么全成功，要么全失败”。**这个说法是残缺的。** 在 Redis 里，这三者**全都不支持 MySQL 那种失败回滚**。

那它们各自到底解决了什么问题？我们挨个拆解。

---

## 一、 管道（Pipeline）：解决“网络慢”

Redis 是一个支持请求/响应协议的 TCP 服务器。普通模式下，客户端向服务器发命令，服务器处理并返回结果，这中间要消耗一次网络往返时间。

**管道的本质就是客户端攒大招**：它允许客户端向服务器发送多个请求，而无需等待回复，最后只需一步即可读取所有回复。

### 验证管道的效率

我们可以做个实验。先在终端准备一个有 10000 条命令的文件：

```bash
seq 1 10000 | awk '{print "SET key:"$1" value:"$1}' > cmds.txt
```

**普通模式发送**（一行行发，等回复）：

```bash
time redis-cli < cmds.txt
```

![管道1.png](/img/Redis/管道1.png)

可以看到，即使是执行极快的简单命令，耗时也比较长，因为时间全耗在了等待网络回复上。

**管道模式发送**（打包全发，最后一次性读）：

```bash
time redis-cli --pipe < cmds.txt
```

![管道2.png](/img/Redis/管道2.png)

从实验结果可以看出，管道让 Redis 的性能得到了巨大的提升，因为它把 10000 次网络 RTT 压缩成了 1 次。

> **注意**：管道仅仅是**客户端**的优化技术。服务端根本不知道你在用管道，它只是收到了一大坨命令，然后挨个执行。**在执行这批命令的过程中，如果其他客户端发来命令，依然可以插队。**

## 二、 事务（Transaction）：解决“执行被打断”

如果我们的业务要求，一批命令在服务端执行时，**中间绝对不能插入其他客户端的命令**，管道就不够用了。这时候需要用到 Redis 事务。

### 1. 与 MySQL 事务的核心分歧

在 MySQL 里，`BEGIN` 开启事务，`COMMIT` 提交。如果中途失败，依靠 undo log 回滚，数据当没发生过。MySQL 保证的是**数据状态的原子性（A）**。

而在 Redis 里，`MULTI` 开启事务，`EXEC` 提交。Redis 依靠单线程一口气把队列跑完。Redis 保证的是**执行过程的连续隔离**。

既然只保证“过程”，那失败了怎么办？因为没有像 MySQL 那样维护回滚日志，如果队列里的某条命令在运行时出错，Redis 无法撤销前面的操作。它的处理方式是：**报错的报错，剩下的继续执行，已执行的绝不回滚**。

这也是为什么官方明确说：**Redis 不支持回滚**。为了极简和高性能，Redis 拒绝擦屁股。

### 2. 事务的执行流程与常用命令

Redis 事务依赖四条指令：

- `MULTI`：用来组装事务，即命令入队；
- `EXEC`：用来执行事务；
- `DISCARD`：用来取消一个事务；
- `WATCH`：用来监视一些 key，一旦这些 key 在事务执行之前被改变，则取消事务的执行。

```shell
redis 127.0.0.1:6379> MULTI 
OK 
redis 127.0.0.1:6379> SET rediscomcn redis 
QUEUED 
redis 127.0.0.1:6379> GET rediscomcn 
QUEUED 
redis 127.0.0.1:6379> INCR visitors 
QUEUED 
redis 127.0.0.1:6379> EXEC 
1) OK 
2) "redis" 
3) (integer) 1
```

看到 `QUEUED` 字样，说明命令成功插入了内存队列，并没有立刻执行。直到调用 `EXEC`，它们才会被连续执行。

### 3. 事务错误的分类与处理方式

Redis 将错误分为两类，采用了极其不同的处理策略：

**第一类：调用 EXEC 之前的错误（入队失败）**
比如命令拼写错误、语法错误、内存不足。只要出现无法写入缓冲队列的情况，Redis 都会记录，在调用 `EXEC` 时，**拒绝执行整个事务**。

```bash
127.0.0.1:6379> multi 
OK 
127.0.0.1:6379> haha //一个明显错误的指令 
(error) ERR unknown command 'haha' 
127.0.0.1:6379> ping 
QUEUED 
127.0.0.1:6379> exec 
//redis无情的拒绝了事务的执行，原因是“之前出现了错误” 
(error) EXECABORT Transaction discarded because of previous errors.
```

**第二类：调用 EXEC 之后的错误（运行时失败）**
比如类型错误（对字符串执行集合操作）。对于应用层面的错误，Redis 认为不是自己该管的问题，所以它**不会理睬这些错误，而是继续向下执行事务中的其他命令**。

```bash
127.0.0.1:6379> multi 
OK 
127.0.0.1:6379> set age 23 
QUEUED 
//age不是集合，所以如下是一条明显错误的指令 
127.0.0.1:6379> sadd age 15 
QUEUED 
127.0.0.1:6379> set age 29 
QUEUED 
127.0.0.1:6379> exec 
//执行事务时，redis不会理睬第2条指令执行错误 
1) OK 
2) (error) WRONGTYPE Operation against a key holding the wrong kind of value 
3) OK 
127.0.0.1:6379> get age "29" 
//可以看出第3条指令被成功执行了
```

### 4. WATCH 命令与乐观锁

事务虽然能保证连续执行，但如果在 `EXEC` 之前，你想要修改的数据被其他客户端改了怎么办？
MySQL 有行锁，Redis 则提供了 `WATCH`，它的机制类似于**乐观锁**。

`WATCH` 可以监视一个或多个 key。如果在调用 `EXEC` 执行事务之前，这些被监视的 key 被修改了，那么整个事务将放弃执行（返回 `nil`）。这就保证了“条件防篡改”。

## 三、 Lua 脚本：解决“复杂逻辑原子化”

事务虽然好，但它不能写 `if-else` 逻辑。如果我要做“判断库存大于0，再扣减”的操作，事务里根本没法表达。

于是 Redis 引入了 Lua 脚本。你可以把一堆逻辑打包发给服务端，让服务端自己算。

- **绝对隔离**：脚本执行期间，Redis 单线程会阻塞其他所有请求（比事务的隔离级别还高）。
- **具备逻辑能力**：可以在脚本里写条件判断、循环。
- **注意**：Lua 脚本执行时如果报错，前面的写操作同样不会回滚。而且如果脚本里写了死循环，会导致整个 Redis 卡死。

## 四、 终极对比与选型建议

为了让你不混淆，我们直接看表格：

| 对比维度 | 管道（Pipeline） | 事务（MULTI/EXEC） | 脚本（Lua Script） |
| :--- | :--- | :--- | :--- |
| **本质** | 客户端网络优化 | 服务端的执行隔离 | 服务端的嵌入式逻辑 |
| **是否支持条件判断** | 否 | 否（仅支持 `WATCH` 乐观锁） | **是**（可写 `if-else`） |
| **执行期间是否被插入** | **会**（随时插队） | **不会**（连续执行） | **绝对不会**（阻塞一切） |
| **遇到运行时错误** | 继续执行，不回滚 | 继续执行，不回滚 | 中断执行，不回滚 |
| **适用场景** | 批量导数据、无需原子性的读写 | 简单的命令打包，防插队，配合 `WATCH` 做乐观锁 | 复杂的业务逻辑（如库存扣减）、分布式锁 |

**实战怎么选？**
- 需要极速导入10万条数据：用 **Pipeline**。
- 需要保证一批命令中间不被别人插队，没有复杂逻辑：用 **事务**。
- 需要做高并发下的库存扣减（查一下，有就减）：用 **Lua 脚本**。
