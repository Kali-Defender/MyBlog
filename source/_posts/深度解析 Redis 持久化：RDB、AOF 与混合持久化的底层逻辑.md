# 深度解析 Redis 持久化：RDB、AOF 与混合持久化的底层逻辑

Redis 是内存数据库，断电或重启会导致内存数据全部丢失。持久化的本质，就是**把数据“留底”到磁盘**。

目前 Redis 提供了三种留底思路：
1. **RDB**：隔一段时间给内存数据“拍张照”，存到磁盘（快照）。
2. **AOF**：把每次“写操作”像记账一样记下来，重启后照着账本重新做一遍（日志）。
3. **混合持久化**：RDB 打底 + AOF 补漏，兼顾速度与安全（Redis 4.0+ 引入，7.4 默认支持）。

---

## 一、RDB：基于 COW 的“拍照”式持久化

### 1. 它是什么
RDB 就是把某一时刻 Redis 内存里的数据，整体保存成一个二进制快照文件（`dump.rdb`）。恢复时，直接拿这张照片还原到拍照那一刻。

### 2. 核心原理：fork 与写时复制（COW）
你敲下 `BGSAVE` 时，Redis 不会阻塞主线程去写盘，而是：
1. **Fork 子进程**：主进程调用 `fork()` 创建一个子进程，这个过程会短暂阻塞主进程。
2. **写时复制（Copy-On-Write）**：子进程与父进程共享内存页。子进程把内存数据写入临时文件；同时，主进程继续处理请求。当主进程修改了某块内存时，内核会为父进程复制一份该页的副本，子进程看到的依然是 `fork` 那一刻的快照。
3. **临时文件替换**：子进程写完临时文件后，原子性地替换旧的 RDB 文件。

> **💡 实验印证**：为什么要先写临时文件再替换？为了防断电。如果直接写原文件，中途断电会导致“半个快照”不可用。这种机制保证了无论何时宕机，磁盘上至少有一份完整的旧快照。

### 3. 致命缺陷：丢失窗口
RDB 是一个**时点快照**，两次快照之间的数据是不在磁盘上的。
> **💡 实验印证**：在我们的实验中，写入 `lab:rdb:before` 后触发 `BGSAVE`，紧接着写入 `lab:rdb:after`。模拟宕机重启后，`after` 查出来是 `nil`。这就是 RDB 的“丢失窗口”，不是 Bug，是它的基因缺陷。

## 二、AOF：基于追加日志的“记账”式持久化

### 1. 它是什么
AOF 不存数据长什么样，而是存“你执行过哪些写命令”。重启时把命令按顺序重放（Replay）一遍。

### 2. Redis 7.4 的真实物理结构
在早期的 Redis 中，AOF 只是一个名为 `appendonly.aof` 的单一文本文件。但从 Redis 7.0 开始，AOF 演变成了**多部分 AOF（Multi-Part AOF）**。在我们的实验中，你会在 `appendonlydir` 目录下看到三个文件：
*   `*.manifest`：清单文件，记录当前使用哪些 AOF 文件。
*   `*.base.rdb`：基础文件（如果是纯 AOF，这里是 AOF 格式；如果开启了混合持久化，这里是 RDB 格式）。
*   `*.incr.aof`：增量文件，记录基础文件生成后的新写命令。

### 3. 刷盘策略与操作系统的“页缓存”
AOF 记录命令分两步：先 `write()` 到操作系统的内存缓冲区（页缓存），再 `fsync()` 真正落盘。
`appendfsync` 决定了 `fsync` 的频率：
*   **`always`**：每写一条命令立刻刷盘。最安全，性能最差。
*   **`everysec`**：每秒刷盘一次（默认）。后台线程异步执行，宕机最多丢 1 秒的数据。可通过 `aof_delayed_fsync` 监控磁盘是否卡顿。
*   **`no`**：完全交给操作系统决定何时刷盘。
    > **💡 避坑概念**：`appendfsync no` **不是不记录**，它依然会写到页缓存，只是不主动触发 `fsync`。因此 `kill -9` 杀进程不会丢数据（数据还在内核缓存里），只有**断电或内核崩溃**才会真丢。

### 4. AOF 重写：给账本“瘦身”
AOF 是追加日志，执行 100 次 `INCR` 会记 100 条，文件会无限膨胀。
AOF 重写（`BGREWRITEAOF`）就是 fork 一个子进程，读取当前内存里的数据，生成**恢复当前数据所需的最少命令集**写入新 AOF，最后替换旧文件。

## 三、混合持久化：Redis 7.4 的“终极方案”

纯 RDB 丢数据多，纯 AOF 文件大、恢复极慢。混合持久化（配置 `aof-use-rdb-preamble yes`）完美解决了这个问题。

### 1. 原理：打底 + 补漏
当你触发 `BGREWRITEAOF` 时，Redis 的子进程不会生成纯文本账本，而是：
1. **打底**：把当前内存数据直接以 **RDB 格式**写成 `base.rdb`。
2. **补漏**：在写 `base.rdb` 期间，主进程收到的新命令，追加到 `incr.aof` 文件中。

### 2. 恢复极速且安全
重启恢复时，Redis 会先**秒读** `base.rdb`（RDB 格式，极快），再回放 `incr.aof` 里的少量增量命令。
> **💡 实验印证**：在我们的实验中，用 `head -c 5` 读取 `*.base.rdb`，开头赫然是 `REDIS` 这 5 个字符。这证明了混合持久化已经生效，底层正在用 RDB 格式作为 AOF 的打底文件。

## 四、总结：RDB 与 AOF 怎么选？

| 对比项 | RDB | AOF | 混合持久化 |
| :--- | :--- | :--- | :--- |
| **本质** | 存数据快照 | 存写命令流水账 | RDB 头 + AOF 尾 |
| **数据完整性** | 较低，可能丢几分钟 | 较高，最多丢 1 秒 | 最高，最多丢 1 秒 |
| **文件大小** | 小 | 大 | 较小（重写后） |
| **恢复速度** | 快 | 慢 | 极快 |
| **适用场景** | 备份、能接受丢数据 | 对数据完整性要求高 | 生产环境首选 |

**官方建议**：直接开启混合持久化（同时保留 AOF 机制）。这样既有 RDB 的备份速度和文件紧凑性，又有 AOF 的低数据丢失率。

---

## 五、核心认知与实验避坑总结

1. **RDB 是“存结果”，AOF 是“存过程”**。
2. **AOF 重写不是修改原文件**，而是生成新文件后再替换，这防止了中途崩溃导致原有账本损坏。
3. **数据安全是分层的**：`write()` 只进内核（防进程崩溃），`fsync()` 才进磁盘（防断电）。理解这一点，你才能真正弄懂 `everysec` 和 `no` 策略的真实风险。
4. **生产环境故障保护**：如果磁盘满或权限错误导致 RDB 写盘失败，Redis 会触发 `MISC` 保护，拒绝写入。这是保护你的数据底线，不要轻易关闭 `stop-writes-on-bgsave-error`。
